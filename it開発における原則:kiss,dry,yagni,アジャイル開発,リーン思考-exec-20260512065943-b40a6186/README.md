## 各原則の要点

### KISS (Keep It Simple, Stupid)
**「シンプルさを設計の最優先とせよ」**

- **問題**: 過剰設計（Over-Engineering）により、デバッグに数時間かかるシステムが生まれる
- **解決**: 50行で解決できるものに500行のフレームワークを使わない
- **注意**: 「シンプル = 低品質」ではない。シンプルさは可読性・保守性の確保

### DRY (Don't Repeat Yourself)
**「システム内の知識は単一・明確・権威ある表現を持つべき」**

- **問題**: コピペプログラミング（WETコード）により、修正漏れでバグが発生
- **解決**: バリデーション・ビジネスロジック等の「知識」を1か所に集約
- **注意**: 「見た目が似たコード」の無理な共通化は密結合を生む（AHA原則）

### YAGNI (You Aren't Gonna Need It)
**「必要になるまで機能を実装するな」**

- **問題**: 未使用機能が開発コストを増大させ、コードベースを複雑化させ続ける
- **解決**: 今のスプリントで必要な機能のみ実装する
- **注意**: 品質軽視ではない。継続的リファクタリング・自動テスト・CIとセットで機能する

| アジャイル原則 | 対応する設計原則 |

## メリット・デメリット

### 3原則を適用するメリット
- 変更コストの削減（修正が1か所で済む）
- バグの早期発見・予防
- チームの開発速度向上（コードが読みやすいため）
- 技術的負債の抑制

### 適用の落とし穴（デメリット）
- **DRYの過剰適用**: マイクロサービス間での共有ライブラリは密結合を生む
- **YAGNI単独適用**: 自動テスト・CIなしに適用すると技術的負債とカオスを生む
- **KISSとの衝突**: シンプルさを追求しすぎると将来の拡張性を損なう場合がある

> **原則はトレードオフを考慮して使うツール。教条主義的な適用は避けること。**
