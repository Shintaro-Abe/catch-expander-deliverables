## 各原則の早見表

### KISS（Keep It Simple, Stupid）
- **意味**: コードをできるだけシンプルに保つ
- **メリット**: 読解・バグ修正・変更が速い
- **注意点**: 「シンプル ≠ 簡単」— シンプルな設計には設計の手間がかかる

### DRY（Don't Repeat Yourself）
- **意味**: 同じロジック・知識を複数箇所に書かない
- **メリット**: 変更箇所を1箇所に集約できる
- **注意点**: 過剰抽象化は密結合を生む。Rule of Three（3回目で抽象化）が指針

### YAGNI（You Aren't Gonna Need It）
- **意味**: 今必要でない機能は実装しない
- **メリット**: 構築・維持・修正コストを削減（Microsoftの研究: 機能の1/3しか価値を生まない）
- **注意点**: リファクタリング習慣とセットで機能する。セキュリティ機能には適用しない

## 原則とアジャイル・リーン思想の関係

```
アジャイルマニフェスト 第10原則:
「シンプルさ――行う作業量を最大限に削減する技法――が本質的である。」
        ↕
  KISS・DRY・YAGNI（XP起源の設計原則）
        ↕
リーン7原則（廃棄物排除・JIT・全体最適）
```

| 設計原則 | リーンのムダ（対応） |
|----------|---------------------|
| YAGNI | 余分な機能（過剰生産ムダ）|
| DRY | コード重複（欠陥・在庫ムダ）|
| KISS | 不必要な複雑性（加工ムダ）|

---

## 原則間のトレードオフ

| 競合 | 解決指針 |
|------|----------|
| DRY vs KISS | 競合時はKISS優先（過剰抽象化より重複許容） |
| DRY vs YAGNI | 「今必要な重複だけを排除」で両立 |
| テストでのDRY | ユニットテストでは隔離性のため意図的重複を許容 |
